# Инструкция для нового агента: как работать по этому пакету

Этот файл — развёрнутое ТЗ для Cursor в **другом** репозитории. Сначала скопируй папки пакета в `.cursor/` нового проекта (см. ниже). Потом открой чат и дай агенту этот файл целиком. Агент обязан следовать ему, а не «угадывать» процесс.

Источник пакета: репозиторий `rinat1313/create_sheme`, ветка `origin/main`. Снимок skills / rules / agents лежит рядом: `cursor-pack/skills`, `cursor-pack/rules`, `cursor-pack/agents`.

---

## 0. Как установить в новый проект (человек делает один раз)

Из корня **нового** репозитория:

```bash
mkdir -p .cursor
cp -a /путь/к/cursor-pack/skills  .cursor/skills
cp -a /путь/к/cursor-pack/rules   .cursor/rules
cp -a /путь/к/cursor-pack/agents  .cursor/agents
git add .cursor
git commit -m "Add TZ workflow Cursor skills, rules and subagents"
git push origin main
```

После копирования:

1. Актуальная копия конфига должна жить в **`origin/main`** нового проекта (правило `cursor-config-on-main`).
2. Папку `.cursor/backup` **не** копируй: там старые агенты (`worker`, `designer`, `tester`).
3. Правило `inspector-editing.mdc` — про инспектор редактора схем. Если в новом проекте нет инспектора — удали этот файл или оставь, он сработает только на `web/js/inspector.js`.
4. Skill `ui-ux` написан вокруг холста/инспектора схем. На этапах UI читай его как стиль интерфейса; конкретные селекторы подстрой под новый продукт.
5. Skill `go-logging` — только если backend на Go. Иначе на этапе кода ставь N/A.

Проверка: в новом проекте должны быть 16 файлов в `.cursor/agents/`, 16 skills, 7 rules (или 6 без inspector).

## 1. Кто ты, если тебе дали этот файл

Ты агент Cursor в новом репозитории. Пользователь хочет **тот же процесс работы**, что в `create_sheme`.

- Если сообщение начинается с **«ТЗ.»** или явно есть техническое задание на изменение продукта — запускай цепочку из 8 этапов. Первым через Task вызывай субагента **`lead`**.
- Если написано **«Не ТЗ.»**, «вопрос», «как запустить», «сделай картинку», «поставь модели» — **не** запускай 8 этапов. Ответь сам по существу.
- Вопросы пользователю задаёт **только lead**. Специалисты, исполнители, тестировщики и писатель **не** пишут пользователю.
- Реализацию кода без финального пула задач (этап 4) начинать **запрещено**.
- Пропуск любого из 8 этапов запрещён. Нет зоны — пиши **N/A** и почему, затем иди дальше.
- Один круг вопросов. Нет ответа — зафиксируй допущения и продолжай. Не жди бесконечно.

Перед чтением skills/rules при работе по ТЗ: `git fetch origin main`. Если локальный `.cursor/` старше `origin/main` — бери файлы с `origin/main`.

## 2. Карта процесса (обязательная)

Простыми словами: пользователь пишет ТЗ → координатор ведёт всю цепочку и один говорит с человеком → команда думает → список задач → код → проверка → справка → отчёт в `main`.

```
Пользователь пишет «ТЗ.»
        ↓
     lead (координатор)
        ↓
1 intake  → analyst → бриф
2 вопросы → все 7 специалистов → один круг A/B/C пользователю
3 решения → специалисты → пакет без противоречий
4 пул     → все группы → без пула не кодят
5 код     → backend / frontend / sql / devops
6 проверка → QA / manual / SQL  --неуспех--> 5
           |                     --10 провалов / слом решения--> 3
7 docs    → technical-writer (help если есть)
8 отчёт   → lead сам, commit/merge/push origin/main
```

«Сломалось решение» на шагах 4 или 5 тоже возвращает на шаг 3, не только «10 раз».

## 3. Skills: что читать и когда

Главный skill: `.cursor/skills/tz-workflow/SKILL.md`. Остальные **дополняют** его, не заменяют.

| Когда | Skill | Что делать |
|-------|--------|------------|
| Любое ТЗ, всегда первым | `tz-workflow` | 8 этапов, кто кого вызывает |
| Этап 1 | `tz-intake` | Принять ТЗ, доступ, бриф; analyst |
| Этап 2 | `tz-questions` | Вопросы специалистов, один круг A/B/C |
| Этап 3 | `tz-solutions` | Решения по зонам, сверка противоречий |
| Этап 4 | `tz-tasks` | Черновой пул, гейт, финальный пул |
| Этап 5 | `tz-execute` | Код исполнителями, локальная проверка своей задачи |
| Этап 6 | `tz-verify` | Тестеры только проверяют; 10 провалов → этап 3 |
| Этап 7 | `tz-docs` | Руководство и help; отдельная задача на тексты для пользователя |
| Этап 8 | `tz-report` | Краткий отчёт + закрытие в main |
| Этапы 1–4 и пересмотр решения | `tz-specialists` | Кого вызывать из специалистов |
| Этапы 4–5 | `tz-executors` | Кого вызывать из исполнителей |
| Этапы 4 и 6 | `tz-testers` | Кого вызывать из тестировщиков |
| Этапы 4 и 7 | `tz-writers` | Вызов technical-writer |
| Frontend/UI | `ui-ux` | Паттерны UI (адаптируй к продукту) |
| Внутри этапа 7 | `user-docs` | Простой язык, слои help/руководства |
| Go-функции | `go-logging` | slog: вход, выход, длительность |

Запрещено: «я сам всё сделаю без lead»; вызов `worker` / `designer` / `tester` / `ui-tester` / `tech-writer`.

## 4. Правила (always-on и git)

Положи в `.cursor/rules/` как есть. Смысл:

| Файл | Суть |
|------|------|
| `tz-workflow.mdc` | Всегда 8 этапов; lead; таблица субагентов |
| `project.mdc` | Стек: микросервисы Go, фронт HTML/CSS/JS; help; схемы на фронт только запрошенные; git в main |
| `commit-to-main.mdc` | После DoD коммит **без** ожидания «закоммить?» |
| `merge-to-main.mdc` | Задача не закрыта, пока нет в `main` |
| `cursor-config-on-main.mdc` | Skills/rules/agents только в `origin/main`; fetch перед чтением |
| `update-user-help.mdc` | Смена UI/логики → обновить help и руководство |
| `inspector-editing.mdc` | Только редактор схем; иначе не трогать |

Конфликт с облачным агентом Cursor (ветка `cursor/*` + PR): в **этом** процессе итог всё равно должен оказаться в `origin/main`. Feature-ветка — промежуточный шаг.

Если в новом проекте другой стек (не Go / не HTML): оставь процесс ТЗ, а в `project.mdc` поправь абзацы «Микросервисы» и «Frontend» под факт. Процесс из 8 этапов не меняй.

## 5. Субагенты: полный список, модели, зона

Все роли — **файлы в `.cursor/agents/`**. Lead вызывает их через **Task**. Линзы «в голове lead» без Task **нельзя**.

В frontmatter каждого файла поле `model:` — одна модель, не список. `inherit` = как родительский чат.

### Координатор

| Subagent | Модель | Делает | Не делает |
|----------|--------|--------|-----------|
| `lead` | `grok-4.6-fast` | 8 этапов, вопросы пользователю, сводка, git, отчёт | Сам не пишет продуктный код, не тестирует «заодно», не пишет help вместо writer |

### Специалисты (этапы 1–4; после 10 провалов снова)

| Subagent | Модель | Смотрит | N/A если |
|----------|--------|---------|----------|
| `analyst` | `grok-4.6-medium` | ТЗ vs продукт, направление, сложность | — (на этапе 1 почти всегда нужен) |
| `architect` | `grok-4.7-high` | Слои, API, границы сервисов | Нет системных границ |
| `ui-ux-designer` | `grok-4.6-medium` | Стиль, паттерны UI, skill `ui-ux` | Нет UI |
| `security` | `grok-4.7-high` | Утечки, атака, секреты | Нет поверхности |
| `algorithmist` | `grok-4.7-high` | Математика, алгоритмы, вероятность | Нет расчётов |
| `programmer` | `grok-4.6-medium` | Паттерны кода, границы модулей, **не** пишет прод-код | Нет кода приложения |
| `database` | `grok-4.6-medium` | Хранение, индексы, ускорение | Нет БД |

### Исполнители (нарезка на 4, код на 5)

| Subagent | Модель | Делает | N/A если |
|----------|--------|--------|----------|
| `backend` | `composer-2.5` | Go API и сервисы | Нет сервера |
| `frontend` | `composer-2.5` | HTML/CSS/JS, `ui-ux` | Нет клиента |
| `sql` | `composer-2.5` | Миграции, запросы | Нет СУБД |
| `devops` | `composer-2.5` | Docker, деплой, конфиги | Нет деплоя |

Composer **без Fast**. Fast дороже в ~6 раз при той же голове.

### Тестировщики (зоны на 4, прогон на 6)

| Subagent | Модель | Делает | Жёсткий запрет |
|----------|--------|--------|----------------|
| `qa-tester` | `composer-2.5` | Код, автотесты, тесты функций | Не правит продукт и docs **во время прогона этапа 6** |
| `manual-tester` | `inherit` | Ручной прогон UI | То же |
| `sql-tester` | `composer-2.5` | БД и SQL | То же |

На этапе 6 тестеры **не чинят**. Нашли дыру → отчёт lead → lead гонит переделку на этап 5.

Про автотесты: QA **описывает/проверяет** тесты. Если в отчёте этапа 5 тестов нет — это дефект исполнения, не «QA дописал прод-код». Новый тест как часть проверки согласуй через lead и пул, не молча в прогоне.

### Техписатели (задача на 4, тексты на 7)

| Subagent | Модель | Делает |
|----------|--------|--------|
| `technical-writer` | `composer-2.5` | Руководство, help простым языком, схемы для пользователя |

Информация для пользователя — **отдельная задача**, не внутри задачи на код.

## 6. Как lead обязан вести этапы (для агента, который вызывает lead)

### Этап 1 — Получение ТЗ (`tz-intake`)

1. Вызови `lead`.
2. Lead читает `tz-intake`, вызывает `analyst`.
3. Analyst: наш ли это продукт, куда движемся, сложность, хватает ли данных.
4. Вопросы на старте — только если без них нельзя начать (полнота, доступ, толкование). Формат: формулировка + A/B/C + «или свой вариант». Не спрашивать «как кодить».
5. Пакет-бриф обязателен. Без вопросов — N/A в пакете.
6. Этап 2 только после брифа.

### Этап 2 — Вопросы (`tz-questions`)

1. Вход: бриф. Не повторять вопросы про доступ.
2. Вызови **всех семь** специалистов. Нет зоны у роли — специалист пишет N/A, это не пропуск вызова.
3. Lead собирает, оставляет пользователю только важное, одним сообщением, варианты A/B/C.
4. Нет вопросов — сразу этап 3.
5. Нет ответа — допущения lead, дальше.

### Этап 3 — Решения (`tz-solutions`)

1. Семь специалистов предлагают решение по своей зоне.
2. Lead **дважды** сверяет противоречия между ролями. Пока спорят — команде кодить нельзя.
3. Пакет для пула задач.

### Этап 4 — Пул (`tz-tasks`)

Режь задачи по зонам: код, база, интерфейс, проверки, тексты. Без списка кодить нельзя.

В пуле у каждой задачи: зона (backend/frontend/sql/devops/docs/test), DoD, зависимость.

Гейт: реализовать набор или вернуть решение на этап 3. Слом набора ≠ возврат на этап 1.

### Этап 5 — Код (`tz-execute`)

Каждый исполнитель пишет **свою** зону и сам проверяет **свою** задачу. Чужие файлы без строки в пуле не трогать.

Нет комментариев в коде. Рабочие Go-функции логируют вход/выход/длительность (`go-logging`).

Отчёт lead: сделано / проблемы / не решено. Недочёт → доработка на 5. Слом решения → 3.

### Этап 6 — Проверка (`tz-verify`)

Lead отдаёт отчёт этапа 5 тестировщикам. Они проверяют. Lead смотрит: что сломано, что не совпало с отчётом (где исполнитель наврал), задачу снова на 5.

10 неуспехов одной задачи → специалисты заново на этапе 3, новый список задач.

Успех → пакет для этапа 7 (что менялось в файлах).

### Этап 7 — Документация (`tz-docs`)

Писатель правит руководство. Help в UI — если в проекте есть (в исходном проекте: `App.showHelp()` в `web/js/app.js`, модалка `#helpModal`). В новом проекте найди аналог help и правь его, если UI/логика менялись.

Простой язык, без внутренних имён пакетов.

### Этап 8 — Отчёт (`tz-report`)

Только после успеха 6 и 7 (или N/A по docs). Кратко:

- что сделано, новые функции, проблемы, что не вышло;
- исходное ТЗ;
- вопросы и ответы;
- решения;
- пул со статусами (выполнено / нет / были проблемы);
- тесты: что гоняли, результат;
- руководство и help;
- рекомендации — необязательно.

Пока нет в `main` — задача не закрыта.

## 7. Git в конце ТЗ

1. Тесты и DoD пройдены.
2. Commit.
3. Если была feature-ветка: `git checkout main && git pull origin main && git merge <ветка>`.
4. `git push origin main`.
5. `git status` чистый, ветка `main`.

Секреты и артефакты сборки не коммитить.

## 8. Что копировать, а что оставить в create_sheme

Копируй всегда: `skills/`, `agents/`, rules процесса (`tz-workflow`, `project` с правкой стека, `commit-to-main`, `merge-to-main`, `cursor-config-on-main`, `update-user-help` с правкой путей help).

Опционально: `inspector-editing.mdc`, `ui-ux` (адаптировать), `go-logging`.

Не копируй: исходный код продукта, `.cursor/backup`, историю чата если не нужна (`user-chat-history.md` — только архив формулировок человека).

## 10. Чеклист агента в новом репозитории (первые 2 минуты)

1. Есть `.cursor/skills/tz-workflow/SKILL.md`? Если нет — остановись и скажи человеку скопировать пакет.
2. Есть 16 файлов в `.cursor/agents/` включая `lead.md`?
3. `git fetch origin main` — конфиг не старше remote?
4. Сообщение пользователя: ТЗ или нет?
5. ТЗ → Task `lead`. Не ТЗ → ответ без 8 этапов.

Если чего-то нет в новом продукте (нет SQL, нет UI) — всё равно вызови роль на своём этапе; роль отвечает N/A. Не выкидывай роль молча.
