# Подготовка вопросов (этап 2)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После пакета этапа 1 (`tz-intake`). `lead` читает этот skill **до** этапа 3. Читай `tz-specialists` и вызывай специалистов через Task. При UI — skill `ui-ux` у `ui-ux-designer`.

Не основной сценарий для этапов 1 и 3–8: вход — пакет `tz-intake`; выход — информационный файл этого skill.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки вопросов.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 3 (`tz-solutions`) начинать **после** информационного файла. Без него — не переходить к решениям.
4. Skills `ui-ux` и `user-docs` — внутри своих этапов, не вместо вопросов.
5. Полноту ТЗ и доступ к материалам не переспрашивать: это этап 1.
6. Координатор — `lead`. Вызывай всех семь специалистов через Task. Вопросы пользователю задаёт только lead.

## Действия lead

1. Взять пакет этапа 1: ТЗ, ответы пользователя, доступ, допущения.
2. Проанализировать пакет: Task на `analyst`, `architect`, `ui-ux-designer`, `security`, `algorithmist`, `programmer`, `database`. Нет зоны — N/A по роли, не пропуск.
3. На критические моменты, без которых нельзя выбрать решение, составить вопросы пользователю. Каждый вопрос: формулировка + варианты + «или свой вариант». Не спрашивать про полноту и доступ.
4. Если критических вопросов нет — **вопросов нет**, информационный файл с N/A, сразу этап 3.
5. Сверить пересечения внутри своих выводов. Внутренний спор пользователю не тащить.
6. Задать пользователю оставшиеся вопросы (один круг). При молчании — допущения.
7. Когда противоречий нет — составить **информационный файл** для этапа 3. Файл — артефакт хода (в промпте), не коммит в репозиторий.

## Формат информационного файла

Короткие секции:

- вход (пакет этапа 1);
- выводы специалистов (или N/A по роли);
- вопросы, которые были (или N/A);
- пересечения и как сняты противоречия (или N/A);
- ответы пользователя / допущения;
- кому передавать (этап 3 — тот же lead).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ).
- Не подменять этап 3 (skill `tz-solutions`).
- Не кодить до финального пула этапа 4.
- Не спрашивать пользователя из агентов специалистов.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить бриф/файл этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Вопросы про полноту ТЗ и доступ на этапе 2.
- Пропуск Task на специалистов (lead сам пишет выводы без агентов).
- Переход к решениям без информационного файла.
- Коммит пакета этапа в `main`.
