# Конвейер ТЗ (tz-pipeline)

При получении ТЗ следовать этому процессу. Оркестратор — субагент `planner`. Специалисты, исполнители и тестировщики — соответствующие project subagents в `.cursor/agents/`.

## Этапы

```text
ТЗ
 → планировщик
 → специалисты (анализ)
 → обратная связь → пул задач
 → исполнители (код)
 → тестировщики
 → проверка специалистов
 → [fail] доработка / другое решение
 → [ok] git + merge в main + отчёт
```

### 1. Приём ТЗ

Планировщик получает ТЗ, уточняет границы (что in/out of scope), не пишет код на этом шаге.

### 2. Анализ специалистами

Планировщик параллельно (где возможно) делегирует:

| Роль | Agent | Фокус |
| --- | --- | --- |
| Аналитик | `analyst` | разбор ТЗ, метрики |
| Архитектор | `architect` | стек, архитектура |
| Алгоритмист | `algorithmist` | алгоритмы (по необходимости) |
| СУБД | `db-specialist` | хранение, Redis/Postgres/иное |
| UI/UX | `uiux-designer` | механики UI/UX (если есть UI) |

Каждый специалист возвращает краткий вердикт: риски, рекомендации, конкретные требования к реализации.

### 3. Пул задач

Планировщик собирает обратную связь, формирует упорядоченный пул задач для исполнителей (зависимости, критерии приёмки).

### 4. Исполнение

| Роль | Agent | Зона |
| --- | --- | --- |
| Программист Go | `go-programmer` | код на Go по ТЗ |
| Программист SQL | `sql-programmer` | SQL/миграции/запросы к СУБД |

Соблюдать project rules: без комментариев в коде; не менять endpoints без явного приказа.

### 5. Тестирование

| Роль | Agent | Зона |
| --- | --- | --- |
| Программист-тестировщик | `unit-tester` | unit-тесты функций/методов |
| QA | `qa-tester` | системные/интеграционные тесты |
| Ручной тестировщик | `manual-tester` | UI/фронтенд вручную |

Тестировщики **не** меняют основной код — только тестовый. Во время фазы тестирования прод-код не правят.

### 6. Проверка специалистами

После зелёных тестов планировщик возвращает результат профильным специалистам. При провале — доработка исполнителями или альтернативное решение, затем снова тесты.

### 7. Завершение

После успеха:

1. Добавить изменения в git (commit).
2. Объединить с основной веткой `main` (PR + merge по принятому процессу репозитория).
3. Написать отчёт планировщика:

```markdown
## Отчёт по ТЗ

### Что сделано
- ...

### Что не сделано
- ...

### Риски
- ...

### Рекомендации
- ...
```

## Правила оркестрации

- Не пропускать этапы анализа для нетривиального ТЗ.
- Не отдавать код в merge без тестов и без проверки специалистов (когда они участвовали).
- Не менять существующие проходящие тесты ради зелёного статуса.
- UI/UX и алгоритмист подключаются только если ТЗ это требует; аналитик, архитектор и СУБД — по умолчанию для backend/данных.
