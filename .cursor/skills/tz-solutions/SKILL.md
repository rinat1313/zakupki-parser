# Подготовка решений (этап 3)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После информационного файла этапа 2 (`tz-questions`). `lead` читает этот skill **до** этапа 4. Читай `tz-specialists` и вызывай специалистов через Task. При UI — skill `ui-ux` у `ui-ux-designer`.

Не основной сценарий для этапов 1–2 и 4–8: вход — ТЗ, вопросы и ответы (файл этапа 2); выход — пакет для пула задач.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки решений.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 4 (`tz-tasks`) начинать **после** пакета этого skill. Без него — не формировать задачи и не кодить.
4. Skills `ui-ux` и `user-docs` — внутри своих этапов, не вместо решений.
5. Новые вопросы пользователю здесь не задавать: это этап 2. Если без вопроса нельзя выбрать решение — lead возвращает на этап 2, не опрос из `tz-solutions`.
6. Координатор — `lead`. Решения — после Task на специалистов `tz-specialists`. Вопросы пользователю задаёт только lead.

## Действия lead

1. Взять ТЗ, вопросы и ответы (информационный файл этапа 2).
2. Подготовить решения по зонам: Task на специалистов `tz-specialists` — API/данные (`architect`), UI/UX или N/A (`ui-ux-designer`), риски ИБ (`security`), алгоритмы или N/A (`algorithmist`), код и паттерны или N/A (`programmer`), хранение и БД или N/A (`database`), соответствие направлению (`analyst`). Не список задач. Не код.
3. Проверить противоречия и пересечения **между ролями**: где решения бьются или вместе могут дать проблему.
4. При риске — пересмотреть стыки и совместимость с уже принятыми решениями. **Ещё раз** проверить все решения. Пока есть конфликт — не идти в этап 4.
5. Когда противоречий нет — подготовить **пакет для формирования пула задач** (этап 4). Пакет — артефакт хода (в промпте), не коммит в репозиторий.
6. Не писать задачи на этом этапе.

## Формат пакета для пула задач

Короткие секции:

- вход (файл этапа 2);
- решения по зонам и ролям (или N/A по роли);
- пересечения и как сняты противоречия (или N/A);
- согласованный набор решений;
- N/A (нет UI / нет API / нет вопросов);
- кому передавать (этап 4 — тот же lead).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ) и этап 2 (опрос пользователя).
- Не подменять этап 4 (список задач).
- Не кодить до финального пула этапа 4.
- Не спрашивать пользователя из агентов специалистов.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить пакет этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Новые вопросы пользователю на этапе 3 вместо возврата на этап 2.
- Один проход сверки: нет повторной проверки после правок.
- Пакет решений превращён в задачи.
- Коммит пакета этапа в `main`.
