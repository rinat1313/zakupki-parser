# Рабочий процесс выполнения ТЗ

Это основной skill при получении ТЗ. Этапы 1–8 детализированы skills `tz-intake`, `tz-questions`, `tz-solutions`, `tz-tasks`, `tz-execute`, `tz-verify`, `tz-docs` и `tz-report`.

Актуальная копия этого skill и остальных `.cursor/skills` — ветка `origin/main` (правило `cursor-config-on-main`). Перед этапами `git fetch origin main` и читай файлы с `origin/main`, если локальный snapshot старше.

Дополнения (не заменяют эту цепочку): `tz-intake` на этапе 1; `tz-questions` на этапе 2; `tz-solutions` на этапе 3; `tz-tasks` на этапе 4; `tz-execute` на этапе 5; `tz-verify` на этапе 6; `tz-docs` на этапе 7; `tz-report` на этапе 8; `tz-specialists` на этапах 1–4 и при пересмотре решения; `tz-executors` на этапах 4–5; `tz-testers` на этапах 4 и 6; `tz-writers` на этапах 4 и 7; `ui-ux` при frontend/UI; `user-docs` — стиль слоёв внутри этапа 7.

## Обязательная цепочка

1. Получение ТЗ.
2. Подготовка вопросов.
3. Подготовка решений.
4. Подготовка задач.
5. Выполнение задач.
6. Проверка выполненной работы.
7. Подготовка документации.
8. Подготовка отчетов.

Пропуск этапов запрещён. Если этап не применим (нет вопросов, нет UI, нет пользовательского поведения), lead явно пишет N/A и почему, затем идёт дальше. Не ждать пользователя бесконечно: один круг вопросов, при молчании — зафиксировать допущения.

## Участники

| Роль | Кто | Где в цепочке |
|------|-----|----------------|
| Lead | subagent `lead` | Этапы 1–8: координация, вопросы пользователю, сводка, git, отчёт |
| Специалисты | subagent через Task | Этапы 1–4; пересмотр решения |
| Исполнители | subagent через Task | Этапы 4–5 |
| Тестировщики | subagent через Task | Этапы 4, 6 |
| Технические писатели | subagent через Task | Этапы 4, 7 |

Каждый пользователь группы — файл в `.cursor/agents/` и вызов через Task. Skills групп (`tz-specialists`, `tz-executors`, `tz-testers`, `tz-writers`) описывают **кого** вызывать, не заменяют Task.

Группа **Специалисты** (lead вызывает через Task): `analyst`; `architect`; `ui-ux-designer`; `security`; `algorithmist`; `programmer`; `database`.

Группа **Исполнители** (lead вызывает через Task): `backend`; `frontend`; `sql`; `devops`.

Группа **Тестировщики** (lead вызывает через Task): `qa-tester`; `manual-tester`; `sql-tester`.

Группа **Технические писатели** (lead вызывает через Task): `technical-writer`.

Не вызывай устаревшие имена `worker`, `designer`, `tester`, `ui-tester`, `tech-writer`. Вопросы пользователю задаёт только `lead`. Реализацию без этапа 4 (списка задач) запрещено начинать.

### Запрещено

- Выполнять ТЗ без чтения этого skill.
- Пропускать lead.
- Считать линзы групп заменой Task: роли — субагенты.
- Считать задачу завершённой до отчёта lead (этап 8) и проверки (этап 6).
- Закрывать ТЗ с пользовательскими изменениями при устаревших help или руководстве.
- Создавать агентов вне списка в `.cursor/agents/`.

## Этапы

### 1. Получение ТЗ

1. Получи ТЗ от пользователя.
2. Вызови `lead` первым.
3. `lead` читает skill `tz-intake` и вызывает `analyst` через Task: предварительная оценка (соответствие приложению, направление, сложность), проверка доступа к материалам, уточняющие вопросы только если без них нельзя стартовать (полнота, доступ, толкование ТЗ). Каждый вопрос — формулировка + варианты на выбор + «или свой вариант». Не спрашивать, как реализовывать.
4. `lead` фиксирует пакет (бриф): исходное ТЗ, ответы/допущения, что есть в доступе, чего нет. Вопросов не было — N/A в пакете.
5. Этап 2 начинать **после** пакета.

### 2. Подготовка вопросов

1. Вход этапа — пакет этапа 1. Не повторять вопросы про полноту ТЗ и доступ к материалам.
2. Читай skill `tz-questions` и `tz-specialists`: lead вызывает всех семь специалистов через Task (при UI — `ui-ux` у дизайнера), критические вопросы или явный сигнал «вопросов нет».
3. Пользователю — только оставшиеся вопросы (через lead).
4. Если вопросов нет — N/A, сразу этап 3.
5. Если ответа нет — `lead` фиксирует допущения и идёт дальше.
6. `lead` составляет информационный файл для этапа 3.

### 3. Подготовка решений

1. Вход этапа — информационный файл этапа 2 (ТЗ, вопросы, ответы).
2. Читай skill `tz-solutions` и `tz-specialists`: lead вызывает специалистов через Task, готовит решения по зонам (или N/A по роли).
3. `lead` дважды проверяет противоречия внутри набора.
4. Без противоречий `lead` готовит пакет для формирования пула задач (этап 4).

### 4. Подготовка задач

1. Вход этапа — пакет этапа 3. Реализацию без финального пула запрещено начинать.
2. Читай skill `tz-tasks`, `tz-specialists`, `tz-executors`, `tz-testers` и `tz-writers`: `lead` вызывает субагентов и создаёт черновой пул по зонам (сложность — `analyst`, зоны — `architect`, исполнение — исполнители, проверка — тестировщики, тексты — `technical-writer`), разбирает его, решает реализовать принятый набор или изменить решение. Другое решение — снова специалисты; оно не должно противоречить уже принятым. Слом набора — возврат на этап 3, не этап 1.
3. После успешной проверки — финальный пул на этап 5 (код, UI, документация этапа 7 — если меняются визуал, логика или сценарии, иначе N/A).

### 5. Выполнение задач

1. Вход этапа — финальный пул этапа 4. Без него — не кодить.
2. Читай skill `tz-execute` и `tz-executors`: lead вызывает исполнителей своей зоны через Task; после задачи — локальная проверка своей реализации, не всего функционала; чужие зоны без явного указания в пуле не трогать.
3. После пула `lead` составляет итоговую информацию: что сделано, какие проблемы, что не удалось решить.
4. Нет проблем — этап 6; недочёт реализации — доработка на этапе 5; слом набора решений — возврат на этап 3 (`tz-solutions`), не этап 1.
5. Если проверка (этап 6) вернула дефекты — вернуться сюда, не на этап 1.
6. При UI — skill `ui-ux`. Логирование функций, без комментариев в коде.

### 6. Проверка выполненной работы

1. Читай skill `tz-verify` и `tz-testers`. `lead` берёт отчёт этапа 5 и вызывает `qa-tester` / `manual-tester` / `sql-tester` через Task.
2. Во время прогона **не** править код, тесты, конфигурацию и документацию «заодно».
3. Неуспех — разбор факта, недоделок и расхождения отчёта с фактом; задача на этап 5 и повторную проверку.
4. Одна задача не получается более 10 раз — заново проанализировать решение этапа 3 со специалистами; иное решение — через этап 3, не тихая правка на 6.
5. Успех всех проверок — пакет для этапа 7: сведения о работе и документы/файлы с изменениями.

### 7. Подготовка документации

1. Читай skill `tz-docs` и `tz-writers`. `lead` берёт пакет этапа 6.
2. Вызывает `technical-writer` через Task и вносит изменения в документацию проекта. Help в UI — если он есть и затронут.
3. Информация для пользователя оформляется **отдельной задачей** (из пула этапа 4 или добавленной lead), не внутри задачи на код.
4. Тексты — простым доступным языком (стиль слоёв — `user-docs`). Нет пользовательских изменений — N/A.

### 8. Подготовка отчетов

1. Читай skill `tz-report`. `lead` пишет отчёт **после** успешной проверки (этап 6) и документации (этап 7 или N/A).
2. Кратко: что сделано, новые функции, проблемы, что не получилось. Обязательные секции: ТЗ пользователя; вопросы и ответы; решения; пул задач со статусами; краткий отчёт по тестам; краткий отчёт по руководству и help. Рекомендации в конце — необязательно.
3. Коммит, merge в `main`, push `origin/main` (см. `commit-to-main`, `merge-to-main`). Задача не завершена, пока изменения не в `main`.
