# Подготовка задач (этап 4)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После пакета этапа 3 (`tz-solutions`). `lead` читает этот skill **до** этапа 5.

Не основной сценарий для этапов 1–3 и 5–8: вход — пакет для пула задач; выход — финальный пул.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки задач.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 5 (`tz-execute`) начинать **после** финального пула. Без него — не кодить.
4. Skills `ui-ux` и `tz-docs` (`user-docs` — стиль, `tz-writers` — вызов `technical-writer`) — внутри своих этапов, не вместо пула. Информация для пользователя — отдельная задача зоны документации, не внутри задачи на код.
5. Новые вопросы пользователю здесь не задавать: это этап 2. Если без вопроса пользователя нельзя выбрать нарезку — lead возвращает на этап 2, не опрос из `tz-tasks`.
6. Координатор — `lead`. Нарезка — Task на `tz-specialists` (сложность, зоны, ИБ/UI/алгоритмы/код/БД если есть в пуле), `tz-executors` (backend / frontend / SQL / DevOps на задачу), `tz-testers` (QA / manual / SQL на проверку) и `tz-writers` (`technical-writer` на тексты). Вопросы пользователю задаёт только lead.
7. Смена решения — снова Task на специалистов `tz-specialists`, затем сверка с набором этапа 3.

## Черновик

1. Взять **полученную информацию**: пакет этапа 3 (согласованный набор решений, снятые пересечения, N/A).
2. Создать **черновой пул задач**, разделённый **по зонам** (код, архитектура/данные, UI, документация), ролям `tz-executors` (если зона исполнения есть), ролям `tz-testers` (если зона проверки есть) и ролью `tz-writers` (если зона текстов есть). Задача без зоны и без трассировки к решению набора — не класть.
3. Lead владеет сборкой пула и сверяет зоны, границы и соответствие набору этапа 3. Не подменять принятые решения новыми «от себя».

## Анализ

1. Разобрать черновой пул по зонам.
2. Собрать внутренние вопросы: неясная нарезка, риск сломать принятое решение, нехватка зоны, пересечение задач. Пользователю не писать. Не кодить.
3. Если вопросов нет — явно: **вопросов нет**.
4. На этом этапе — разбор пула, не реализация.

## Решение: реализовать или изменить

1. Разобрать внутренние вопросы.
2. Если набор этапа 3 можно сохранить — **реализуем** принятые решения: правка формулировок, порядка, N/A по зоне. Повторная сверка черновика.
3. Если нужно **изменить решение** — другое решение **не должно противоречить уже принятым**. Lead вызывает специалистов `tz-specialists` через Task и проверяет стык с набором этапа 3.
4. Уточнение, которое **не ломает** согласованный набор — остаётся на этапе 4, повтор анализа.
5. Изменение, которое **ломает** набор (другая граница, отказ от принятого, решение вне пакета 3) — **возврат на этап 3** (`tz-solutions`), не тихая перепись пула и не этап 1.
6. После любого изменения пула или решения — ещё раз проверить противоречия. Пока конфликт или открытые внутренние вопросы — не этап 5.

## Финальный пул

Когда противоречий нет и проверка создания пула успешна — lead фиксирует **пул задач** и передаёт на этап 5. Пул — артефакт хода (в промпте), не коммит в репозиторий.

## Формат пула задач

Короткие секции:

- вход (пакет этапа 3);
- пул по зонам, ролям исполнения (`tz-executors` или N/A), ролям проверки (`tz-testers` или N/A) и ролью текстов (`tz-writers` или N/A);
- трассировка задача → решение набора;
- внутренние вопросы и как сняты (или N/A);
- реализовать набор / правка внутри 4 / возврат на этап 3;
- кому передавать (этап 5 — тот же lead).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ), этап 2 (опрос пользователя), этап 3 (новые решения без сверки).
- Не кодить до финального пула.
- Не спрашивать пользователя из агентов групп.
- Не принимать решение, которое противоречит уже принятым.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить пул этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Пул из воздуха, без пакета этапа 3.
- Сразу кодить с черновика.
- Тихая смена решения, которая ломает набор этапа 3.
- Новое решение без проверки на противоречие принятому.
- Коммит пакета этапа в `main`.
