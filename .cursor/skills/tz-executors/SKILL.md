# Исполнители

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Каждый пользователь группы — **subagent** в `.cursor/agents/`. `lead` вызывает их через Task на этапе выполнения.

## Когда включать

Lead читает этот skill на этапе **4** (нарезка пула по зонам исполнения) и на этапе **5** (`tz-execute`, код по зоне). На этапах 1–3 исполнители не выбирают архитектуру вместо специалистов. На этапах 6–8 не заменяют прогон, docs и отчёт.

Не основной сценарий для закрытия ТЗ: выход — реализация по зоне и пометки N/A, не отдельный workflow.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — маршрут вызова исполнителей внутри этапов 4–5.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Вызывай через Task: `backend`, `frontend`, `sql`, `devops`. Не вызывай `worker`.
4. Проектирование — специалисты. Исполнители не пересматривают набор решений этапа 3. Слом набора — возврат на этап 3.
5. Frontend опирается на skill `ui-ux`, не вместо него. Backend — на `go-logging` при новых рабочих функциях Go.

## Группа

| Роль | Агент | Что делает | Когда N/A |
|------|-------|------------|-----------|
| Backend программист | `backend` | Бэкенд на основном языке проекта (Go); паттерны без лишних абстракций | Нет серверного кода, API, сервисов — N/A |
| Frontend программист | `frontend` | Фронтенд на основном стеке (HTML/CSS/JS); паттерны UI-кода | Нет UI/клиента — N/A |
| SQL программист | `sql` | Функционал и скрипты СУБД, миграции, запросы, данные | Нет БД, миграций, SQL — N/A |
| DevOps | `devops` | Конфиги, скрипты развёртывания, Docker | Нет деплоя, контейнеров, инфраструктуры — N/A |

Все четыре роли обязательны к вызову на этапе 5, если задача в пуле. Нет зоны в задаче — N/A по роли, не пропуск всей группы.

## Действия lead

1. На этапе 4 (`tz-tasks`): у каждой задачи зоны исполнения — backend / frontend / SQL / DevOps (можно несколько). Нет зоны — не назначать роль.
2. На этапе 5 (`tz-execute`): Task только на назначенные роли; чужие зоны не трогать.
3. Локальная проверка — в рамках своей зоны задачи, не этап 6.
4. Несколько ролей в одной задаче — lead вызывает каждую по очереди через Task.

Выводы ролей — в отчёт этапа 5 (короткие пункты или N/A), не отдельные файлы в git.

## Стоп-лист

- Не заменять Task «линзой без агента».
- Не второй workflow вместо `tz-workflow`.
- Не кодить до финального пула этапа 4.
- Не пропускать назначенную роль без N/A.
- Не подменять специалистов на этапах 1–3.
- Не спрашивать пользователя из этих агентов.

## Антипаттерны

- Lead пишет код всех зон сам без Task.
- Frontend пишет API, backend правит CSS без задачи в пуле.
- SQL навязывает миграцию без хранения в ТЗ.
- DevOps добавляет Docker «на будущее».
- Исполнитель меняет принятое решение этапа 3 из паттерна.
