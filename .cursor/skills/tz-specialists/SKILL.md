# Специалисты

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Каждый пользователь группы — **subagent** в `.cursor/agents/`. `lead` вызывает их через Task, не проходит роли «линзами без Task».

## Когда включать

Lead читает этот skill на этапах **1–4** (оценка ТЗ, вопросы, решения, нарезка задач) и при **пересмотре решения** (порог 10 из `tz-verify`, слом набора на этапах 4–5). На этапах 5–8 эти роли не заменяют код, прогон, docs и отчёт.

Не основной сценарий для закрытия ТЗ: выход — выводы по ролям (или N/A), не код.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — маршрут вызова специалистов внутри этапов.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Вызывай через Task: `analyst`, `architect`, `ui-ux-designer`, `security`, `algorithmist`, `programmer`, `database`. Не вызывай устаревшие `designer`, `worker`.
4. Вопросы пользователю задаёт только lead (этапы 1–2). Выводы специалистов пользователю не тащить сырьём.
5. UI-роль опирается на skill `ui-ux`, не вместо него.

## Группа

| Роль | Агент | Что смотрит | Когда N/A |
|------|-------|-------------|-----------|
| Аналитик | `analyst` | Соответствие ТЗ приложению; направление развития; сложность задач | ТЗ не про продукт (чисто внутренний конфиг без влияния на направление) — кратко N/A |
| Архитектор | `architect` | Архитектура, внедрение технологий, границы сервисов и данных | Нет изменений API/данных/слоёв — N/A |
| UI/UX дизайнер | `ui-ux-designer` | Современный стиль, паттерны оформления, skill `ui-ux` | Нет frontend/UI — N/A |
| Специалист по ИБ | `security` | Утечки, поверхность атаки, доступ к данным и секретам | Нет данных, сети, файлов, auth — N/A с явной пометкой |
| Алгоритмист | `algorithmist` | Математика, алгоритмы, вероятность, физика моделей | Нет расчётов, графов, геометрии, вероятностей — N/A |
| Специалист по программированию | `programmer` | Написание кода, теория, паттерны разработки | Нет изменений кода приложения — N/A |
| Специалист по базам хранения данных | `database` | Базы данных, оптимизация и ускорение работы хранилища | Нет хранения, запросов, индексов, схемы БД — N/A |

Все семь ролей обязательны к вызову (или явный N/A от агента). Пропуск роли без N/A запрещён.

## Действия lead

1. На этапе 1 (`tz-intake`): Task на `analyst` — соответствие, направление, грубая сложность; остальные — только если без них нельзя понять полноту ТЗ. Не выбирать архитектуру на этапе 1.
2. На этапе 2 (`tz-questions`): Task на все семь агентов; критические вопросы или «вопросов нет» по роли.
3. На этапе 3 (`tz-solutions`): Task на специалистов; решения с учётом всех неприменённых-как-N/A ролей; сверка противоречий между ролями (два прохода, сводит lead).
4. На этапе 4 (`tz-tasks`): Task на `analyst` (сложность нарезки), `architect` (зоны); остальные — если зона есть в пуле.
5. Порог 10 (`tz-verify`) или слом набора: снова Task на все семь, затем этап 3.

Выводы ролей — в пакет этапа (короткие пункты или N/A), не отдельные файлы в git.

## Стоп-лист

- Не заменять Task «линзой без агента».
- Не второй workflow вместо `tz-workflow`.
- Не кодить из этих ролей до финального пула этапа 4.
- Не пропускать роль без N/A.
- Не отдавать пользователю внутренний спор ролей: сводит lead.
- Не спрашивать пользователя из этих агентов.

## Антипаттерны

- Lead сам пишет выводы специалистов без Task.
- ИБ пропущен, потому что «это же внутренний инструмент».
- Алгоритмист пишет формулы там, где ТЗ про кнопку.
- Аналитик оценивает календарные сроки.
- Программист навязывает паттерн без нужды в коде.
- Специалист по БД предлагает индексы и смену схемы без запросов и хранения.
